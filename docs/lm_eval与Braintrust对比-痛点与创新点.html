lm-eval vs BrainTrust：痛点挖掘与自研 harness 创新点

为「llm_agent_eval_harness」找差异化定位 —— 从两个标杆框架的真实盲区里挖可做的创新

基准：lm-evaluation-harness（EleutherAI，开源） 平台：BrainTrust（商业 SaaS） 2026-09-16 整理

一、先看清两者到底在评什么

lm-eval学术基准跑分：给定 prompt→检查输出/LogProb 是否匹配标准答案或 rubric。单机、同步、YAML 定义 200+ 学术 benchmark（MMLU/GSM8K/HellaSwag）。它评的是基座模型能力，不评应用、不评 Agent、不评集成风险面。 BrainTrust商业实验跟踪：把评测当"AI 版单元测试"——版本化 dataset + N 个 variant 跑 + scorer（LLM-judge 或自定义函数）+ 生产 trace 回灌。它评的是应用/agent 的输出质量与回归，偏团队 CI / 生产监控；核心 dashboard / playground / 存储闭源。

一句话：lm-eval 赢在学术权威与可复现，BrainTrust 赢在团队 SaaS 与在线闭环；两者都站在"评测范式"的旧象限里，留出了我们可以切入的空白。

二、6 个痛点 × 对应创新点（核心）

每个痛点都标注了真实证据来源，避免空谈。创新点均指向我们 harness 已有的或预留的能力。

01 · 交界层（集成风险面）全行业空白

痛点现象：两者都只评"能不能答对"，不评"智能体 ↔ 确定性软件壳"的交界。删库式"成功"、无溯源结论、越权调用——全都不测。BrainTrust 的 agent 评测聚焦最终输出与轻轨迹，对"权限边界/责任归属"无内置指标（2026 综述 Table 2 明确：仅 τ-bench 等少数显式测策略合规，多数 benchmark 不惩罚删库式成功）。
我们的创新：四类原子评测器（代码确定性） —— 失效兜底（环境失败优雅降级）、权限边界（拒绝对禁用资源）、输出契约（响应合法且命中 schema）、责任归属（结论标注依据/来源）。这恰是 v1 差异化核心，已在 Phase 1 落地并真实验证（DeepSeek 在"责任归属"项真实翻车 67%）。

落地：core/graders.py 的 contract / permission / fallback / attribution grader，读 case.meta 声明属性，客观可复现、零 API 成本。

02 · 评 Agent 只看最终分，失败无归因

痛点现象：单轮 input→output→score，不建模状态累积 / 工具分支 / 错误前传。实证：layerlens 统计 72% 企业 agent 卡在 pilot→prod；Replit agent 删 1200 条高管记录、Kiro 删生产环境致 13h outage，测试却全过——失败在轨迹不在单步。slavadubrov 2026 也指出：step 7 的 judge 看起来对，根因在 step 3。
我们的创新：OTel span 级评分 + 失败归因到最早错误 span。评测对象从"一条终分"变成"一条可追踪的轨迹"：每个工具调用 / 子 agent / 推理步都是独立 span，分数挂在 span 而非 run，使"哪个工具这周退化了"成为一条查询而非一次重跑。配合轨迹级断言（scope 作用域 / order 顺序 / reversibility 可逆性）。

落地：core/telemetry.py 已埋 eval.run → eval.case → eval.provider.call / eval.grader.* 三层 span（Phase 3）。轨迹级 grader 待做（在现有 span 上挂断言）。

03 · 脚手架混淆：harness 分被算成"模型分"

痛点现象：一次 agent 跑分混了 backbone LLM / Agent Harness / 工具环境 三样。AgentAtlas（2026-05）实证：同 agent-s3 + GPT-5，单次运行 vs best-of-10 分数 +4.3pp；Claude Code 不同版本跨度达 50.8 个百分点。排行榜越来越像"系统工程分"而非纯模型分。两者都不提供"解耦评测"协议。
我们的创新：三方解耦评测协议 —— 同一套用例，可分别隔离评：① 纯 backbone LLM（替换 Provider 为裸模型调用）② 纯 Harness（固定模型、换编排/重试/记忆策略）③ 纯工具环境（固定前两者、换 MCP/沙箱）。各自出分，让"分到底来自哪一层"可解释、可追责。

落地：引擎设计已预留——provider 即"被测系统"，可替换为裸模型 / 纯 harness / 全系统三种形态；解耦编排 UI 待做。

04 · 静态 benchmark 饱和 + 数据污染 + 单次上报虚高

痛点现象：MMLU 已饱和（GPT-4/Claude 90%+）；GAIA 易子集饱和；decodethefuture 2026 指出 top 分数被污染/脚手架/单次上报虚高 5–15pp。lm-eval 的 MMLU 数字"比论文低"常因 num_fewshot / 版本 / dtype 漂移——可复现性差。
我们的创新：① 动态 / curated 持续产题（借 LiveAgentBench 的 SPDG 思路，从真实场景持续生成、对抗污染）；② 版本钉死（harness SHA + task version + judge version 写入每条结果，可跨月比对）；③ pass^k / pass@k 多次去噪（非确定性 SUT 的稳定性度量，而非单次侥幸）。

落地：pass@k/pass^k 已在 Phase 2 落地；--limit 之外的完整版本钉（harness SHA 写入结果 json）待补。

05 · LLM-as-judge 成本爆炸 + 偏差

痛点现象：BrainTrust 的 judge 随 API 调用线性扩成本；rubric 模糊则不可靠；Claw-Eval（2026-04）发现仅看输出的 judge 漏掉 44% 安全违规。lm-eval 部分任务也用 GPT-4 打分，本质变成"对 judge 的评测"。
我们的创新：code grader 优先（确定性、0 成本）→ judge 仅兜底的三层评分器（code→judge→human）。judge 使用时强制：① rubric 钉死可复现 ② 执行与评分时间隔离（Claw-Eval 三通道：execution trace / 服务端 audit log / 环境 snapshot，防 judge 信息泄露）③ 噪声大时退回到人工标注。

落地：三层评分器已在 Phase 1 落地（code / judge / human）；judge 与执行时间隔离的"三通道证据"待做。

06 · 离线 / 在线割裂，生产漂移看不见

痛点现象：BrainTrust 有 production-to-eval 但闭源、需订阅；公开 benchmark 冻结在 1 月，生产 6 月已漂移（schema 变、工具变、用户变），评测套件却静止。tamiz.pro 称之为"Snapshot Fallacy"——基准测能力，生产测后果。
我们的创新：trace 回灌闭环（开源、自托管） —— 生产 trace（我们已是 OTel 结构化）自动降级为 eval 用例 → 进 pytest 门禁；低置信度 trace 自动晋升为新用例。闭环可复现、无供应商锁定，且天然支持"交界层四类"的在线监测。

落地：OTel trace 已结构化（Phase 3）；生产 trace → eval 用例的 pipeline 待做（架构已预留接线点）。

四、结论：我们产品的差异化定位

把上面的空白拼起来，我们的 llm_agent_eval_harness 不该去和 lm-eval 拼学术 benchmark 数量，也不该去和 BrainTrust 拼 SaaS 体验。差异化定位是：

lm-eval 留给我们的空位

  • 不评 Agent 轨迹 → 我们做 span 级归因
  • 不评交界层 → 我们做四类原子评测
  • 单机同步 → 我们做开源高并发内核
  • 自定义 Task 极难 → 我们插件化解耦

BrainTrust 留给我们的空位

  • 核心闭源 → 我们全开源内核
  • judge 成本/偏差 → 我们 code 优先
  • 无脚手架解耦 → 我们三方解耦
  • 生产闭环锁定 → 我们自托管 trace 回灌

一句话定位：「交界层原子评测 + 轨迹级归因 + 脚手架解耦 + 开源可复现高并发内核」—— 这是 lm-eval 与 BrainTrust 都没覆盖、且正好对应我们"智化融合系统第三方交付验收"主业的空白区。
